Architecture note · HSS Central Financial Control · Production pathway

From an 18-tab workbook to an intranet service — same architecture, only the labels change

The slide's claim holds for this workbook: browser → server → database. The workbook already is that architecture in disguise — registers are tables, pivots are views, formulas are rules, the yellow cells are the write API, and the "Checks" tab is the test suite. This note maps each tab to its production component, lists the file formats each tier is written in, and states what the final deployed output actually is.

Read this first — one structural disagreement with the phrase "the same Excel can be a live site". In production the Excel stops being the source of truth. PostgreSQL becomes the source of truth; the workbook becomes a controlled import format (on-ramp) and a regenerated output (off-ramp, GET /export.xlsx). If two things can both be edited, one of them is a copy — and the control model in tab 00 says explicitly it is "not an accounting ledger" and depends on human assurance. Human assurance is far easier to enforce on a database with roles and an audit log than on a file that anyone can Save-As. The test harness delivered alongside this note keeps the Excel as the source on purpose — that is what makes it a test, not a system.

3 · How data moves

xlsx (today)→importers/xlsx_importer.py + import_spec.json→Pydantic validation (types, enums, FKs)→PostgreSQL tables→SQL views = pivots→FastAPI /api/v1→React pages→GSIB browser on intranet
human confirms (yellow cell)→POST/PATCH with SSO identity + evidence ref→audit_log row + register row→run_controls() → exceptions→views refresh→GET /export.xlsx regenerates the 18 tabs

The importer is the only place the workbook layout is known. import_spec.json (sheet · header row · first column · optional last column, per table) is checked in; when a tab moves, the spec changes, nothing else does. The test harness uses the identical spec in the browser.

5 · Deployment on the intranet

Runtime

One intranet host (or a small VM pair) running docker-compose: nginx (serves dist/, proxies /api), the FastAPI container, and PostgreSQL. TLS from the internal CA; hostname on the internal DNS; users arrive from GSIB devices with SSO. Nothing here needs internet egress — Google Fonts in the harness must be replaced with self-hosted fonts in production.

Pipeline (.gitlab-ci.yml)

lint → pytest (rules + checks + acceptance) → vite build → docker build → deploy. A failing 15_Checks-equivalent fails the pipeline, so REVIEW status cannot silently reach production.

6 · The prototype pathway (the slide's left box) — and where the test harness sits

Stage 0 is the delivered test harness: a single .html that embeds the workbook as JSON, re-implements the formulas in JavaScript, and reconciles them against the workbook's own pivot tabs. It proved the rules tie (FY26 forecast 130,200; FY27/28 195,300; monthly 16,275; Jira & Confluence driver mismatch +120; 5 critical / 2 warning / 5 overdue / 3 mismatches). Stage 1 is the slide's "Today's stack" — Express.js + SQLite, same JSON shapes, run locally, so the API contract is exercised before Python is written. Stage 2 is the production stack above. The process is identical across all three; only the labels change.

7 · What architecture cannot fix

Four of the five open critical exceptions are business definitions, not engineering gaps: Finance allocation missing (EXC-001), official AOR references (EXC-002), Azure PO→AOR mapping (EXC-003), and the Actual Spend recognition point (EXC-004). The schema can hold a column for each; it cannot decide them. Ship the system with those columns nullable and the checks failing loudly, exactly as the workbook does today — that honesty is the control.

Also unresolved by design: the Cross-FY attribution rule (17_Demo, Blocked) and the AOR→cost-stream mapping (why the cost-stream pivot shows AOR allocation 0 across the board — the workbook has no such mapping, and neither will the database until Finance supplies one).
